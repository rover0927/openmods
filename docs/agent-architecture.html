01 / Overview

一次用户请求的完整链路

从浏览器发一条消息，到模型流式回复、工具执行、子代理结算，全部围绕一个核心：会话日志是事实源，上下文是每步实时投影出来的。server 只负责门控与广播，真正的循环在 agent-core。

apps/server/src/index.ts packages/agent-core/runtime.ts packages/agent-core/session-log.ts packages/agent-core/surface.ts
主链路 分支 / 事件 说明 箭头 = 调用或事件方向

入口只做门控

同一个会话不允许两轮并发：waiting（等子代理）优先于 busy，因为派发发生在回合内，两个条件会同时成立，只有 waiting 能给出准确原因。归档会话直接 409。

日志才是事实源

runtime 只往 SessionLog 追加事件并 emit；SSE 由 server 统一写。刷新页面时靠 Last-Event-ID 补发，语义与实时流一致。

每步重算上下文

系统提示、工具表、surface 都是每一步现算。计划模式、待办、技能白名单在回合中途变化，下一步立即生效。

收尾不是结束

主会话回合结束后还要走 afterRootTurn：有移交就续跑，有子代理就等待，有结算就开汇总回合。真正空闲才给前端 waiting=[]。

if (isSubagent) return settleChild(parent, s)
afterRootTurn(s, result)
02 / Server

有状态的那一层

server 持有会话表、JSONL 日志、SSE 写端与插件注册表。它不实现推理，只负责把运行时需要的依赖装配好，并把运行时产生的事件分发给浏览器。

启动期装配请求期

createSession 同时服务新建与恢复

先占位日志、再读 meta，这样“新建后刷新/重启”仍然是同一个会话。cwd 的优先级是：meta → 显式参数 → 父会话 → 新工作区。

画布归属有兼容分支

新子代理用自己的 id 作画布；只有“老会话没有 canvasId”时才沿父链回溯。新数据不会被旧兼容逻辑改写。

插件顺序是硬约束

功能声明必须先于开关解析。先解析再发现，会让插件自带的开关永远无效，requires 也就永远关不掉。

SSE 一个端点包打天下

open 帧带会话树，断线按 seq 补发；画布快照与增量都走同一条连接，子代理的独立画布也实时可见。

03 / Context

日志 → surface → LLM messages

会话不是内存里不断增长的 messages 数组，而是 append-only 的 JSONL 事件流。每一步请求前，都从日志重新折叠出这一轮要发给模型的上下文。

packages/agent-core/session-log.ts packages/agent-core/surface.ts
投影主链压缩

两层投影，职责分开

buildSurface 处理语义：哪条消息被压缩覆盖、哪些附件这轮不发；buildLlmMessages 处理协议：tool_calls、tool_call_id、image_url 这些 provider 字段。

压缩是影子化

旧消息不删，只被标记 shadowed；摘要作为一条新条目插在末尾。日志仍然可完整回放，模型只看到压缩后的视图。

思考过程不进上下文

assistant/message.reasoning 会落盘（单步截断 64k）用于回放，但 buildSurface 不读取它，避免多轮推理无限膨胀。

请求期才碰字节

图片和文件在日志里都只是引用。这样日志可以安全落盘、可 diff，模型也能按需读取文件而不是把字节塞进上下文。

}

04 / System Prompt

一条字符串，固定拼接顺序

buildSystemPrompt 不是模板文件，而是每步现拼的 string[]。顺序本身就是优先级：人格在最前，行为约束在最后。

按此顺序 push条件段
1角色→ 2当前会话→ 3工作目录→ 4授权→ 5计划模式→ 6当前待办→ 7# 工具→ 8# 可插拔技能→ 9建模流程（无角色）→ 10systemSections→ 11# 回复风格→ 12refine 约束

角色即人格

lead 负责创意与方案、mcmod 负责实施、modeling 只画布、coding 直接改代码。角色还带 toolFilter 与 skills，所以提示与工具天然一致。

现场每步现算

会话现场、待办、计划模式都可能在一轮中途变化；每步重拼保证模型看到的是最新状态，而不是回合开始时的快照。

工具段是“投影结果”

提示里列的工具来自 selectTools，所以计划模式隐藏 exit_plan_mode 之外的门控工具也会同步消失，不会出现“提示里有、请求里没有”。

技能只给目录

技能正文可能很长，系统提示只放名字和一行描述，并明确要求“不加载不要假装读过”。这是渐进披露的关键约束。

05 / Skills & Tools

技能是提示词包，工具是函数表

技能来自文件系统（skills/<name>/SKILL.md），工具来自插件注册的数组。两者在请求体里汇合：技能只出现在系统提示，工具同时出现在提示和 llm.chat({ tools })。

apps/server/src/skills.ts apps/server/src/index.ts · load_skill packages/agent-core/runtime.ts · selectTools
注入链路按需加载

技能是目录，不是数据库

一个技能就是一个目录：SKILL.md + 可选的 references/。扫描失败或目录不存在时返回空列表，不影响启动。

两道白名单

功能开关决定技能“是否存在”，角色 profile.skills 决定“谁能加载”。运行时在 load_skill 里还会再校验一次，防止模型越权。

渐进披露

把整本技能塞进系统提示会挤占上下文，也可能让模型“假装读过”。openmods 只给目录，正文按需读，且明确要求不加载就不要引用。

工具是同一个数组

内置工具和插件工具没有区别：都 push 进 tools，都按角色裁剪。所以“关掉画布”等于画布工具和 modeling 角色一起消失。

tsapps/server/src/skills.ts · DirSkillProvider.scan()
private scan() {
  if (!existsSync(this.skillsDir)) return []
  const out = []
  for (const d of readdirSync(this.skillsDir, { withFileTypes: true })) {
    if (!d.isDirectory() || d.name.startsWith('.')) continue
    const file = join(this.skillsDir, d.name, 'SKILL.md')
    if (!existsSync(file)) continue
    const raw = readFileSync(file, 'utf8')
    const fm = /^---\r?\n([\s\S]*?)\r?\n---/.exec(raw)
    const name = fm?.[1].match(/^name:\s*(.+)$/m)?.[1]?.trim() ?? d.name
    const description = fm?.[1].match(/^description:\s*(.+)$/m)?.[1]?.trim() ?? ''
    out.push({ name, dir: join(this.skillsDir, d.name), description })
  }
  return out
}

06 / Agent Loop

一步 = 一次 LLM 请求

runTurn 是一个有预算的 for 循环。模型每步要么给出工具调用（继续），要么给出最终正文（收尾）；运行时负责把工具结果写回日志，让下一步看到。

packages/agent-core/runtime.ts · runTurn()
每步路径退出条件

每步都重建请求

工具表、系统提示、surface 全部重算。压缩钩子也在步首执行，所以“这一步的上下文”永远是当前会话状态的函数。

流式只影响展示

delta 边到边推给前端，但落盘的是完整 assistant/message。断线重连时回放的是整段，不是碎片。

工具串行，闸门统一

授权、计划模式、未知工具都在 runtime 判定，插件只写 execute。这样每个插件不用重复实现安全策略。

超限只重试一次

上下文溢出会触发 overflowHooks 做最大化收缩，然后 不推进 stepNo 重试；只给一次机会，避免死循环。

tspackages/agent-core/runtime.ts · runTurn() 主循环
for (stepNo = 1; stepNo <= maxSteps; stepNo++) {
  if (signal.aborted) { aborted = true; break }
  const stepId = `${turnId}s${stepNo}`

  // 每步前：压缩钩子（省 token 机制挂载点）
  for (const hook of registries.beforeStepHooks) await hook({ session: rt, abort })

  deps.log.append('step/start', { turnId, stepId })

    rt.getSurfaceMessages(),

    model: rt.getModelLlmId(),

    onReasoningDelta: (delta) => rt.emit('assistant/reasoning', { turnId, stepId, delta }),
  })

  deps.log.append('assistant/message', { turnId, stepId, text: res.text, toolCalls: res.toolCalls })

  if (res.toolCalls.length) {
    for (const call of res.toolCalls) {
      deps.log.append('tool/call', { turnId, stepId, callId: call.id, name: call.name, args: call.args })

      // …未知工具 / 计划模式拦截 / guardApproval / def.execute(args, exec)…
      deps.log.append('tool/result', { turnId, stepId, callId: call.id, name: call.name, forModel: result.forModel })

07 / Finish

一轮到底怎么算结束

收尾不是“模型说完了”，而是运行时给出一个明确的 reason：natural / step-limit / aborted。server 再根据这个 reason 决定要不要自动续跑、等待或汇总。

packages/agent-core/runtime.ts · runTurn() 尾部 apps/server/src/index.ts · afterRootTurn()
正常收尾异常 / 截断中止

三种 reason，三种后续

  • natural：正常汇报，主会话可进入空闲或继续等子代理。
  • step-limit：mcmod 角色会自动续跑，最多 2 次。
  • aborted：直接结束，不自动续跑。

空回复不是错误

模型只输出思考、正文为空时，运行时先给一次“请给出可见回复”的临时提示；仍为空就写兜底文本。用户永远不会看到空气泡。

turn/end 是唯一收口

无论正常、截断还是异常，都在 finally 里落 turn/end。日志回放与前端状态都靠这一条事件对齐。

server 侧还有一层

子代理先写 status 再 settleChild；主会话走 afterRootTurn：移交续跑 → 等待子代理 → 汇总 → 自动续跑 → 真正空闲。

tspackages/agent-core/runtime.ts · 收尾与 turn/end

  reason = hitStepLimit ? 'step-limit' : aborted ? 'aborted' : 'natural'

  rt.emit('turn/end', { turnId, text: finalText, aborted, reason })
}

tsapps/server/src/index.ts · afterRootTurn()
function afterRootTurn(s, result) {
  // ① lead → mcmod 移交：用本回合用户需求自动续跑，不需要用户重发
  const handoff = s.pendingHandoff
  if (handoff) {
    s.pendingHandoff = undefined
    return void runSessionTurn(s, { text: handoff.text, profile: 'mcmod' })
  }
  // ② 还有子代理在跑：锁住输入，等结算
  const waiting = waitingRows(s)
  if (waiting.length > 0) {
    s.sse.send('session/waiting', { sessionId: s.id, waiting })
    return
  }
  // ③ 结算已到：开汇总回合
  if (s.settlements.length > 0) return void maybeAutoContinue(s)
  // ④ mcmod 步数用尽：自动续跑（上限 2 次）
  if (maybeAutoContinueAfterStepLimit(s, result)) return
  // ⑤ 真正空闲
  s.sse.send('session/waiting', { sessionId: s.id, waiting: [] })
}
08 / Dispatch

派发 = 一个会建会话的工具调用

主代理（lead）不亲自建模：它调用 spawn_modeling_subagent，server 立刻创建一个子会话并后台启动回合。子代理有自己的日志、上下文与独立画布，但继承父会话的工作目录与模型。

派发主链父会话状态

为什么用工具而不是特判

派发就是一个普通工具调用：模型决定何时派、派几个、任务怎么写。server 只负责校验与建会话，不需要在提示里写死流程。

共享工作区，不共享画布

所有子代理与父会话共享 cwd，所以读同一份工程；但每个子代理用自己的 canvasId，互不覆盖，右侧页签可切换查看。

父会话被“锁”住

派发后主代理应立即收尾。waiting 非空时 /chat 直接 409，用户无法插话；这是为了避免两轮同时改同一份工作区。

子代理是无人值守的

modeling 角色排除了 spawn / 终端 / 提问 / 计划等工具，收尾固定写“验收点”，因为它等不到任何人回答弹窗。

function startSubagent(parent, input) {
  if (parent.mode === 'subagent') throw new Error('子代理不能再派发子代理（深度上限 1）')
  if (isArchivedLineage(parent.id)) throw new Error('会话已归档，不能再派发子代理')
  if (!profileRegistry.has('modeling')) throw new Error('建模功能已关闭')
  if (liveSubagentCount(parent.id) >= maxActiveSubagents()) throw new Error('并发子代理已达上限')

  const id = randomUUID().slice(0, 8)
  const child = createSession(id, {
    parentId: parent.id,
    cwd: parent.cwd,                 // 工作目录继承；画布不继承（用自己的 id）
    agentName: name,
    description: input.description,
    modelId: parent.runtime.currentModelId,
  })
  child.status = 'running'

  // 派发即登记：waiting 是“还没回来”的唯一事实源
  parent.waiting.add(child.id)
  parent.sse.send('subagent/updated', { childId: child.id, name, status: 'running' })
  parent.sse.send('session/waiting', { sessionId: parent.id, waiting: waitingRows(parent) })

  void runSessionTurn(child, { text: input.prompt, profile: 'modeling' })
    .catch(e => {
      // 兜底：回合在结算前炸掉也要解锁，否则主会话永远卡在等待态
      if (parent.waiting.has(child.id)) {
        child.status = 'error'
        child.lastError = e?.message ?? String(e)
        settleChild(parent, child)
      }
    })
  return child
}

结果怎么交回发起者

子代理跑完后，server 把它从父会话的 waiting 里移除，写进结算收件箱；当最后一只落地时，自动以一条 user 消息的形式唤醒父会话开一轮汇总。

结算主链分支

结算只做三件事

通知面板、从 waiting 出队、把结果放进收件箱。它不直接调用模型，也不拼提示——真正的唤醒交给 maybeAutoContinue。

为什么等“最后一只”

批量派发时逐个唤醒会产生多次半成品汇总。等 waiting 清空再开一轮，主代理能一次拿到全部汇报，也避免回合互相打断。

模型侧就是普通 user 消息

结算消息在日志里带 source.kind='subagent-settled'，但 buildSurface 把它当普通 user 消息投影。区别只在 UI 渲染与溯源，不增加模型侧协议。

汇总回合有独立预算

SETTLEMENT_MAX_STEPS = 12：只做汇报与验收，不能把执行回合的 40 步额度烧在核对上。提示里也明确要求不要批量修补、导出或重跑。

function settleChild(parent, child) {
  notifySubagentUpdate(child)
  const owed = parent.waiting.delete(child.id)      // 是否属于本批派发
  const status = child.status
  const closingText = child.lastText || ''
  const settled = {
    childId: child.id,
    name: child.agentName ?? child.id,
    description: child.description,
    status,
    stopReason: stopReasonOf(status),
    closingText,
    summary: summarize(closingText || child.lastError || '', 160),
  }

  // 关闭自动唤醒：批量派发也只落通知行，主会话不会自己开新一轮
  const autoWake = settingsStore.getPrefs().autoWake
  if (!owed || !autoWake) {
    const notice = { kind: 'subagent-settled', form: 'notice', ...settled }
    parent.log.append('subagent/notice', notice)
    parent.sse.send('subagent/notice', { sessionId: parent.id, ...notice })
    if (owed) parent.sse.send('session/waiting', { sessionId: parent.id, waiting: waitingRows(parent) })
    return
  }

  parent.settlements.push(settled)                       // 结算收件箱
  parent.sse.send('session/waiting', { sessionId: parent.id, waiting: waitingRows(parent) })
  if (parent.waiting.size === 0) void maybeAutoContinue(parent)
}

const SETTLEMENT_MAX_STEPS = 12   // 汇总回合独立预算

async function maybeAutoContinue(parent) {
  if (parent.busy || parent.autoTurn) return
  if (parent.waiting.size > 0 || !parent.settlements.length) return
  if (isArchivedLineage(parent.id)) { parent.settlements = []; return }

  const batch = parent.settlements.splice(0)
  parent.autoTurn = true
  try {
    await runSessionTurn(parent, {
      text: formatSettlementPrompt(batch, parent.profile),
      profile: parent.profile,                 // 必须与会话当前角色一致
      maxSteps: SETTLEMENT_MAX_STEPS,
      source: {                                // 钉在 user/message 上的归属
        kind: 'subagent-settled', form: 'notice',
        settled: batch.map(b => ({ childId: b.childId, name: b.name, status: b.status, summary: b.summary })),
      },
    })
  } finally {
    parent.autoTurn = false
    // 汇总期间又到一批：复查一次，避免被静默吞掉
    if (!parent.busy && parent.waiting.size === 0 && parent.settlements.length > 0)
      void maybeAutoContinue(parent)
  }
}
